# Kustomize Integration Guide for Password Pusher Pro

This guide explains how to use Kustomize with the Password Pusher Pro Helm chart for advanced customizations without forking the chart.

## What is Kustomize?

Kustomize is a Kubernetes native configuration management tool that lets you customize raw, template-free YAML files for multiple purposes, leaving the original YAML untouched and usable as is.

### Kustomize vs Helm Values

| Use Case | Helm Values | Kustomize |
|----------|-------------|-----------|
| Standard configuration | ✅ Perfect fit | Overkill |
| Adding labels/annotations not exposed by chart | ❌ Not possible | ✅ Ideal |
| Injecting sidecars | ❌ Not possible | ✅ Ideal |
| Modifying resource fields chart doesn't expose | ❌ Not possible | ✅ Ideal |
| Patching security contexts | ⚠️ Limited | ✅ Full control |
| Multi-environment overlays | ⚠️ Via multiple values files | ✅ Native support |

### Benefits of Using Kustomize with Helm

- **No forking required**: Customize upstream charts without maintaining a fork
- **Template-free**: Works with raw YAML, no templating syntax to learn
- **Native to kubectl**: Built into `kubectl apply -k` since Kubernetes 1.14
- **Argo CD compatible**: First-class support in Argo CD
- **GitOps friendly**: Pure YAML that's easy to version control and review

## Integration Methods

There are two primary ways to use Kustomize with the Password Pusher Pro Helm chart:

### Method 1: Kustomize as Helm Post-Renderer (Recommended)

Helm renders the chart first, then Kustomize patches the output. This is the most flexible approach and works well with Argo CD.

**Best for:**
- Adding organizational labels/annotations
- Injecting monitoring sidecars
- Modifying resources the chart doesn't expose via values
- Quick patches without changing how you use Helm

### Method 2: Native Kustomize Helm Integration

Kustomize inflates Helm charts directly via the `helmCharts` directive. The chart is fetched and rendered by Kustomize itself.

**Best for:**
- Organizations standardizing on Kustomize as the primary tool
- Complex multi-layer overlays
- When you want Helm to be an implementation detail

## Method 1: Helm Post-Renderer

### Local Development

#### Step 1: Create a Post-Renderer Script

Create `renderer.sh`:

```bash
#!/bin/bash
# Save Helm output and run Kustomize

cat - > helm-output.yaml
kustomize build . && rm helm-output.yaml
```

Make it executable:
```bash
chmod +x renderer.sh
```

#### Step 2: Create kustomization.yaml

```yaml
# kustomization.yaml
resources:
  - helm-output.yaml  # This will be generated by Helm

# Add common labels to all resources
commonLabels:
  app.kubernetes.io/managed-by: kustomize
  cost-center: "12345"
  environment: production
  team: security

# Add annotations
commonAnnotations:
  external-dns.alpha.kubernetes.io/hostname: "pwpush.example.com"

# Apply patches
patches:
  - path: patches/custom-resource-limits.yaml
  - path: patches/add-monitoring-labels.yaml
```

#### Step 3: Create Patches

Create a `patches/` directory with your customization files:

**`patches/custom-resource-limits.yaml`** - Override resource limits:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: pwpush-pro
spec:
  template:
    spec:
      containers:
        - name: pwpush-pro
          resources:
            limits:
              cpu: 1000m
              memory: 1Gi
            requests:
              cpu: 250m
              memory: 512Mi
```

**`patches/add-monitoring-labels.yaml`** - Add monitoring labels to the Service:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: pwpush-pro
  labels:
    monitoring: "true"
    scrape-port: "8080"
```

**`patches/inject-monitoring-sidecar.yaml`** - Add a monitoring sidecar:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: pwpush-pro
spec:
  template:
    spec:
      containers:
        - name: datadog-agent
          image: datadog/agent:latest
          env:
            - name: DD_APM_ENABLED
              value: "true"
          resources:
            limits:
              cpu: 100m
              memory: 256Mi
```

#### Step 4: Deploy with Helm

```bash
# Create values file
cat > values-custom.yaml <<EOF
license:
  key: "your-license-key"
  region: "your-region"

secrets:
  existingSecretName: pwpush-pro-secrets

ingress:
  enabled: true
  className: nginx
  hosts:
    - host: pwpush.example.com
      paths:
        - path: /
          pathType: Prefix
EOF

# Deploy with post-renderer
helm install pwpush-pro pwpush-pro/pwpush-pro \
  --values values-custom.yaml \
  --post-renderer ./renderer.sh
```

### Argo CD with Post-Renderer

Argo CD supports post-renderers via a Configuration Management Plugin (CMP).

#### Step 1: Create the CMP Configuration

Create a ConfigMap with the plugin definition:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: kustomized-helm-cmp
  namespace: argocd
  labels:
    app.kubernetes.io/part-of: argocd
data:
  plugin.yaml: |
    apiVersion: argoproj.io/v1alpha1
    kind: ConfigManagementPlugin
    metadata:
      name: kustomized-helm
    spec:
      version: v1.0
      generate:
        command: [sh, -c]
        args:
          - |
            helm template "$ARGOCD_APP_NAME" . \
              --namespace "$ARGOCD_APP_NAMESPACE" \
              --values values.yaml \
              --include-crds > helm-output.yaml &&
            kustomize build . &&
            rm helm-output.yaml
      discover:
        find:
          command: [sh, -c]
          args:
            - test -f kustomization.yaml && test -f Chart.yaml
```

Apply it:
```bash
kubectl apply -f kustomized-helm-cmp.yaml
```

Restart Argo CD repo-server:
```bash
kubectl rollout restart deployment argocd-repo-server -n argocd
```

#### Step 2: Create Argo CD Application Using the Plugin

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: pwpush-pro
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/your-org/pwpush-pro-kustomize
    targetRevision: main
    path: overlays/production
    plugin:
      name: kustomized-helm
  destination:
    server: https://kubernetes.default.svc
    namespace: pwpush
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

## Method 2: Native Kustomize Helm Integration

This method uses Kustomize's built-in Helm support to inflate charts directly.

### Prerequisites

Enable Helm support in Kustomize:

```bash
# For local Kustomize
export KUSTOMIZE_ENABLE_HELM=true

# Or use the flag
kustomize build --enable-helm .
```

### Local Development

#### Step 1: Create Base Configuration

Create a directory structure:
```
base/
├── kustomization.yaml
└── values.yaml
```

**`base/kustomization.yaml`**:

```yaml
helmCharts:
  - name: pwpush-pro
    repo: https://apnotic.github.io/pwpush-pro-helm
    version: 0.1.1
    releaseName: pwpush-pro
    namespace: pwpush
    valuesFile: values.yaml

# Apply patches after Helm renders
patches:
  - path: patches/add-labels.yaml
  - path: patches/add-annotations.yaml
```

**`base/values.yaml`**:

```yaml
license:
  key: "your-license-key"
  region: "your-region"

secrets:
  existingSecretName: pwpush-pro-secrets

ingress:
  enabled: true
  className: nginx
  hosts:
    - host: pwpush.example.com
      paths:
        - path: /
          pathType: Prefix
```

#### Step 2: Create Environment Overlays

Create overlays for different environments:

```
overlays/
├── production/
│   ├── kustomization.yaml
│   └── patches/
│       └── resource-limits.yaml
└── staging/
    ├── kustomization.yaml
    └── patches/
        └── staging-labels.yaml
```

**`overlays/production/kustomization.yaml`**:

```yaml
resources:
  - ../../base

namespace: pwpush-production

namePrefix: prod-

commonLabels:
  environment: production
  cost-center: "12345"

patches:
  - path: patches/resource-limits.yaml
```

**`overlays/production/patches/resource-limits.yaml`**:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: pwpush-pro
spec:
  replicas: 3
  template:
    spec:
      containers:
        - name: pwpush-pro
          resources:
            limits:
              cpu: 1000m
              memory: 1Gi
            requests:
              cpu: 500m
              memory: 512Mi
```

**`overlays/staging/kustomization.yaml`**:

```yaml
resources:
  - ../../base

namespace: pwpush-staging

namePrefix: staging-

commonLabels:
  environment: staging

patches:
  - path: patches/staging-labels.yaml
```

#### Step 3: Build and Apply

```bash
# Build for production
kustomize build --enable-helm overlays/production

# Apply to cluster
kustomize build --enable-helm overlays/production | kubectl apply -f -

# Or using kubectl directly
kubectl apply -k overlays/production --enable-helm
```

### Argo CD with Native Helm Support

Argo CD requires enabling Helm support in Kustomize globally.

#### Step 1: Enable Helm in Argo CD

Patch the `argocd-cm` ConfigMap:

```bash
kubectl patch configmap argocd-cm -n argocd --type merge \
  -p '{"data":{"kustomize.buildOptions":"--enable-helm"}}'
```

Or apply via YAML:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: argocd-cm
  namespace: argocd
data:
  kustomize.buildOptions: "--enable-helm"
```

#### Step 2: Create Argo CD Application

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: pwpush-pro-production
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/your-org/pwpush-pro-kustomize
    targetRevision: main
    path: overlays/production
  destination:
    server: https://kubernetes.default.svc
    namespace: pwpush-production
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

## Common Customization Examples

### Adding Organizational Labels

All cloud providers support cost allocation via labels:

```yaml
# patches/cost-labels.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: pwpush-pro
  labels:
    cost-center: "12345"
    department: "engineering"
    project: "security-tools"
    owner: "platform-team"
---
apiVersion: v1
kind: Service
metadata:
  name: pwpush-pro
  labels:
    cost-center: "12345"
    department: "engineering"
```

### Adding External-DNS Annotations

For automatic DNS registration:

```yaml
# patches/external-dns.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: pwpush-pro
  annotations:
    external-dns.alpha.kubernetes.io/hostname: "pwpush.example.com"
    external-dns.alpha.kubernetes.io/ttl: "300"
```

### Injecting a Monitoring Sidecar

Add a Prometheus exporter or APM agent:

```yaml
# patches/prometheus-sidecar.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: pwpush-pro
spec:
  template:
    spec:
      containers:
        - name: prometheus-exporter
          image: prom/node-exporter:latest
          ports:
            - containerPort: 9100
              name: metrics
          resources:
            limits:
              cpu: 100m
              memory: 128Mi
```

### Customizing Security Context

For organizations with strict security policies:

```yaml
# patches/security-hardening.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: pwpush-pro
spec:
  template:
    spec:
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
        runAsGroup: 1000
        fsGroup: 1000
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: pwpush-pro
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop:
                - ALL
          volumeMounts:
            - name: tmp
              mountPath: /tmp
            - name: cache
              mountPath: /opt/PasswordPusher/tmp
      volumes:
        - name: tmp
          emptyDir: {}
        - name: cache
          emptyDir: {}
```

### Adding Network Policies

Restrict pod-to-pod communication:

```yaml
# patches/network-policy.yaml

kind: NetworkPolicy
metadata:
  name: pwpush-pro
spec:
  podSelector:
    matchLabels:
      app.kubernetes.io/name: pwpush-pro
  policyTypes:
    - Ingress
    - Egress
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              name: ingress-nginx
      ports:
        - protocol: TCP
          port: 80
  egress:
    - to:
        - namespaceSelector: {}
      ports:
        - protocol: TCP
          port: 53
        - protocol: UDP
          port: 53
    - to:
        - podSelector:
            matchLabels:
              app.kubernetes.io/name: postgresql
      ports:
        - protocol: TCP
          port: 5432
```

## Best Practices

### 1. Use Helm Values When Possible

Kustomize should be for "last-mile" customizations. If the chart exposes it via values, use values:

```yaml
# Good: Using Helm values for standard configuration
replicaCount: 3
resources:
  limits:
    cpu: 1000m

# Good: Using Kustomize for things Helm doesn't expose
commonLabels:
  cost-center: "12345"  # Your org's requirement, not the chart's
```

### 2. Pin Chart Versions

Always pin to specific chart versions for reproducibility:

```yaml
helmCharts:
  - name: pwpush-pro
    version: 0.1.1  # Pin this!
    # NOT: version: latest
```

### 3. Layer Your Configuration

Use a base + overlays pattern:

```
├── base/              # Common configuration
│   ├── kustomization.yaml
│   └── values.yaml
└── overlays/
    ├── production/    # Production-specific patches
    └── staging/       # Staging-specific patches
```

### 4. Never Patch Secrets

Don't use Kustomize to modify secrets. Instead:
- Pre-create secrets and reference them via `existingSecretName`
- Use External Secrets Operator
- Let the chart auto-generate and preserve secrets

### 5. Version Control Your Patches

Store Kustomize configurations in Git alongside your application code or in a dedicated infrastructure repository.

### 6. Test Locally First

Always build locally before applying:

```bash
# See what will be applied
kustomize build --enable-helm overlays/production

# Save to file for review
kustomize build --enable-helm overlays/production > rendered.yaml
```

### 7. Use Strategic Merge Patches

Kustomize uses strategic merge patches by default. Understand when to use different patch types:

```yaml
# Strategic merge (default) - merges lists
patches:
  - path: deployment-patch.yaml

# JSON Patch 6902 - for precise modifications
patchesJson6902:
  - target:
      group: apps
      version: v1
      kind: Deployment
      name: pwpush-pro
    path: json-patch.yaml

# Strategic merge with target
patches:
  - target:
      kind: Deployment
      name: pwpush-pro
    patch: |
      - op: replace
        path: /spec/replicas
        value: 5
```

## Troubleshooting

### Error: "helmCharts is not enabled"

**Cause**: Kustomize Helm support is disabled by default.

**Solution**:
```bash
# For local
kustomize build --enable-helm .

# For Argo CD, patch the ConfigMap
kubectl patch configmap argocd-cm -n argocd --type merge \
  -p '{"data":{"kustomize.buildOptions":"--enable-helm"}}'
```

### Error: "unable to find Chart"

**Cause**: Helm repository not added or chart version doesn't exist.

**Solution**:
```bash
# Verify chart exists
helm search repo pwpush-pro/pwpush-pro --versions

# Check your kustomization.yaml version field
```

### Patches Not Applying

**Cause**: Target name or kind doesn't match.

**Solution**:
```bash
# See what resources exist
kustomize build --enable-helm . | grep -E "^(apiVersion|kind|metadata)"

# Ensure your patch targets match exactly
```

### Argo CD Sync Failures

**Cause**: Kustomize version mismatch or missing `--enable-helm`.

**Solution**:
1. Check Argo CD Kustomize version: `argocd version`
2. Verify `kustomize.buildOptions: --enable-helm` in `argocd-cm`
3. Restart repo-server after ConfigMap changes
